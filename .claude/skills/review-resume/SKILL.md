以 HR 和技术面试官的视角审查简历文件 $ARGUMENTS（默认为 resume.md），评估内容质量并给出改进建议。

## 核心原则

- HR 过简历可能只有 10 秒，简历必须在 10 秒内让人记住你
- 关键词：**简洁清晰、简练不废话、内容有亮点**
- 可以适当包装，可以保持沉默，但必须诚实
- 有数据支撑、可量化的内容更有说服力

## 审查维度

### 1. 个人信息

- 邮箱是否专业（避免纯数字 QQ 邮箱，如 `123456@qq.com`）
- 不应包含家庭住址
- 博客/GitHub 链接是否简短易读
- 是否包含不必要的照片（技术岗通常不需要）

### 2. 自我介绍

- 是否简练，突出个人特色和亮点
- 是否位于项目经验之前
- 是否避免了主观、无法验证的描述（如"吃苦耐劳""善于学习""抗压能力强"）
- 是否用事实而非主观判断来展示能力

### 3. 技能描述

- 是否谨慎使用"精通"二字（无 100% 把握勿用）
- 技能描述是否体现深度理解，而非简单罗列框架名称
  - ✅ `深度掌握 React 技术栈，有大型项目 SSR 实践经验`
  - ❌ `熟悉 React`
- 是否将 AJAX 等技术误称为"语言"
- 是否列举了不必要的基础技能（如 JSON 解析、Git 基础操作）
- 技能列表是否精简有代表性，避免篇幅过长

### 4. 工作经历

- 是否按倒序排列（最近的在前）
- 职位职责是否清晰明确（不过于笼统也不过于详细）
- 是否有量化数据支撑（性能提升百分比、用户量、PV 等）
- 是否突出了个人贡献而非仅描述团队工作
- 是否避免了薪资相关信息

### 5. 项目经验

- 项目简介是否简洁（一句话说清楚项目做什么）
- 是否区分了"项目职责"和"技术实现"
- 是否标注了团队规模或个人/团队开发
- 已上线项目是否提供了可访问的链接
- 是否避免了描述流产/失败项目
- 是否突出技术复杂度，而非使用营销语言
- 是否省略了简单的后台管理等低复杂度项目
- 项目之间是否有相关性和技术成长的延续性

### 6. 语言表述

- 是否避免了口语化表达，保持专业语气
- 是否避免了带有抱怨的词语（如"老板没钱""资源不多"）
- 是否使用确定语气，避免"认为、觉得、应该"等不确定词语
- 是否避免了贬低他人的表述
- 是否避免了技术无关的内容（PS、驾照、重装系统等）

### 7. 亮点加分项（检查是否已充分展示）

- 开源项目贡献或自研开源组件
- 高质量个人博客（原创、有深度）
- 阅读源码的习惯
- 跨领域技能或多语言能力

## 输出格式

```
## 简历审查报告

### 整体评价
（1-2 句话总结简历整体印象，模拟 HR 10 秒扫描的感受）

### 亮点
- ...

### 需改进
- **[维度]** 具体问题描述 → 改进建议

### 建议优先级
1. （最重要的改进项）
2. ...
3. ...
```
